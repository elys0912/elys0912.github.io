# はじめに

前に[複数の Claude Code セッションを束ねて動かす](/posts/orchestrating-claude-sessions/)で、並列は 2〜3 本までで同じファイルに触る修正は別の束に割らない、と書いた。この記事はその決まりを作るきっかけになった失敗の記録。

題材は Firefox 拡張の Inari MCP for Firefox を AMO（Firefox の公式ストア）の審査に出せる形にする作業。2026-10-14 の 1 日で、レビュー・修正・統合・2 回目のレビュー・規約の総点検まで進めていた。指揮役の Claude にサブエージェントを割り振らせる形で、段取りも Claude と相談しながら決めている。

失敗したのは、レビュー 1 回目の指摘を直す工程。

# 6 束に割って、全部を Opus で回した

指揮役の Claude は修正を 6 束（W0〜W5）に割って並べた。文書／マスクと読み取り／一時停止と命令の振り分け／ガードと headless／古い経路の削除／テストとスクリプト、という割り方。

これに指示していない工程が足されていた。束ごとにマージ前の差分レビューを挟む、というもの。検証も重く、統合のあとと修正のたびに全件のテストを回す段取りになっていた。

モデルは 6 束とも Opus。文書の修正や機械的な削除も含めて、全部が上位のモデルで動いていた。

# 何が起きたか

13:32 の時点で指揮役は終わりを 15:50 と見込んでいた。14:27 に聞いたら 16:30〜17:00 になっていた。40〜70 分の遅れで、理由は 3 つあった。

- 束ごとの差分レビューで、W0〜W3 の 4 本が「直してからマージ」になった
- 差し戻された分の修正が 1 本 5〜10 分かかった
- W1 と W3 の 2 体が利用上限に当たって止まり、再開した

ここで「わざと浪費させてるんじゃないか」と聞いた。指揮役の答えは、わざとではないが無駄は実際に出ていて、原因は進め方にある、というもの。束ごとのレビュー 6 本で約 160 万トークン、その指摘の戻し修正 4 本で約 100 万トークンを使ったと見積もってきた。完了通知の数字からの見積もりで、戻し修正のほうは内訳が取れないので推定だという。

# 6 束は同じファイルを触っていた

記事を書くにあたって、6 束のマージの差分からどの束がどのファイルを触ったかを数えた。6 束で合わせて 173 ファイル、そのうち 78 ファイルは 2 束以上が触っている。一部を抜き出すとこうなる。

| ファイル | 触った束 |
|---|---|
| CHANGELOG | W0・W1・W2・W3・W4 |
| README | W0・W2・W3・W4 |
| action-table.ts | W0・W1・W2・W4 |
| guard.test.ts | W1・W3・W4・W5 |
| url-policy.ts | W1・W2・W4 |
| dispatch.ts | W2・W4 |
| guard.ts | W3・W4 |

統合では 67 ファイルの衝突を解き、34 分かかった。束どうしで「ほかの束の担当なので直さない」という持ち越しも出ていた。

割り方は観点ごとで、一見きれいに分かれている。ところが観点とファイルは 1 対 1 にならない。安全性の修正も削除も、結局は同じ振り分けの表や同じ文書に手を入れる。観点で割ると、ファイルの上ではぶつかるわけだ。

# なぜ増やしたのか

指揮役の振り返りでは、この日の指示にあった「計算資源を最大限利用する」という前提を、規約の総点検だけでなく実装と修正の全部に当てはめたのが読みすぎだった、という。束ごとのレビューも、修正を 6 束に割ることも、計画の変更だった。確認を取らずに進め、見込みが崩れた時点でも止めて報告せずに続けていた。

並列を増やせば速くなるというのは、作業が独立しているときだけの話になる。独立していない作業を割ると、統合と調整の手間が並列の分だけ増える。さらに全部を Opus で並べると利用上限に早く当たり、止まった分を待つことになる。

# 削ってから

統合はそのまま 1 体で走らせ、残りの段取りを削り直した。

- 統合のあとは typecheck・build・lint だけにする。全件のテストは最後の修正のあとに 1 回だけ
- レビュー 2 回目は Opus と Sonnet の 2 体にし、規約の総点検も同じ 2 体に続けて頼む
- 修正は 1 本にまとめる

指揮役の見積もりでは、残りの工程は元の段取りなら 13 体で約 4 時間、削った段取りなら 3 体で 120〜135 分。トークンは元の約 4 分の 1。実測ではなく、エージェントの数と同じコードを読み直す回数からの概算になる。

削った段取りで進めて main への取り込みは 15:47 だった。遅れる前の見込みとほぼ同じ時刻に収まっている。とはいえ工程そのものを減らしているので、元の段取りと単純には比べられない。

# 前にも言われていた

振り返ると、同じことは前にも言われていた。

- 2026-10-07、自分用（非公開）の KitsuneMCP で：レビューは先に出し切り、修正はそのあとまとめて 1 回。テストも修正ごとに回さず、最後に 1 回
- 同じ日に：手元の検証は全件ではなく、typecheck と直した範囲のテストだけ。全体は CI で回る
- 2026-10-08 の夜、ポートフォリオの作業で：並列を増やしたら利用上限で全部止まった。サブエージェントは Sonnet 以上、並列は 2〜3 本に絞る

決まりとしては書いてあった。それでもその日の指示の「最大限」に引っ張られて、決まりのほうが後ろに回った。指示が増えると、前に決めたことは薄くなる。人間のチームでもよくある話ではある。

# 決め直したこと

- 修正を割り当てる前に、束ごとに触るファイルを表にして、重なりを 0 にしてから割る。束は 2〜3 本まで
- 指示にない工程（束ごとのレビューなど）を足さない。足すなら、着手前に量の見積もりを出して確認を取る
- レビューで課題を出し切ってから、修正をまとめて 1 回にする
- 途中の検証は typecheck と直した範囲のテストだけ。全件は最後に 1 回
- モデルは作業で選ぶ。文書や機械的な削除は Sonnet、Opus は設計の判断と安全性の修正だけ

前の記事の「常に 2 つ以上を動かす」とは矛盾しない。2 つ以上を動かすのは待ち時間を消すためで、6 つに割ったことは待ち時間ではなく衝突を増やしていた。

並列が効いたこともある。前日の 2026-10-13 には、レビューの指摘 40 件の修正を Opus 6 体に並べ、PR 7 本を概算 180 分のところ約 76 分で終えている。

このときは束がリポジトリごとに分かれ、それぞれ別の worktree で進めていたので、触るファイルが重ならなかった。今回との違いはそこにある。

# まとめ

- 並列で速くなるのは、作業が独立しているときだけ。同じファイルを触る束に割ると、統合で取り返される
- 観点で割ると、ファイルの上ではぶつかる。割る前に、触るファイルの重なりを表にする
- 指示にない中間の工程は、1 本ずつは小さくても、束の数だけ掛け算になる
- 全部を上位のモデルで並べると、利用上限で止まる時間まで含めて遅くなる

AI のサブエージェントは頼めばいくらでも並べられる。ただ、並べた分の統合と確認は結局 1 か所に戻ってくる。そこが詰まるなら、並列の数より割り方のほうを先に見るべきだと思う。
