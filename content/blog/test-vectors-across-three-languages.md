# はじめに

サイトの 2048 は、ブラウザで遊んだ手の列をサーバーが再生してスコアを計算している（不正対策の話は[別の記事](/posts/game-ranking-anti-cheat/)に書いた）。この形だと、ブラウザの TypeScript とサーバーの Java が、同じ種と同じ手の列から 1 ビットも違わない盤面を作らないといけない。どこかでずれると、正しく遊んだ人のスコアが「盤面が動かない手がある」として 400 で弾かれる。

そこで仕様を 1 つの文書にまとめ、Python で参照実装を書いて検査用データ（テストベクタ）を作り、TS と Java のテストに同じファイルを流すことにした。作業は AI（Claude Code）と壁打ちしながら進めている。この記事は言語の違うコードを同じ答えに縛るための作りを書く。

# 置いてあるもの

リポジトリの `testdata/game-2048/` に置いてあるのは 3 つだけ。

| ファイル | 中身 |
|---|---|
| README.md | 仕様。乱数、盤面、タイルの出現、手、再生、ベクタの形 |
| reference.py | 参照実装。Python の標準ライブラリだけで書いてある |
| vectors.json | 検査用データ。reference.py が作る |

正は vectors.json で、TS も Java もこれを読む側に回る。ケースを足すときは reference.py を直して作り直し、vectors.json も同じコミットに含める。生成は決定的なので、仕様を変えずに作り直して差分が出たら、参照実装かデータのどちらかが壊れている。この記事を書く前に手元で作り直してみたら、差分は 0 だった。

参考にしたものが Python だったので、参照実装も Python で書いている。

最初に作った reference.py と vectors.json は、リポジトリの外のメモ置き場に作っていた。リポジトリに写したあとも古い方が残っていて、後のレビューで比べると vectors.json は 399 行違い、古い参照実装には種の範囲の検査も UTF-16 の長さの扱いも無かった。古い方から作り直していたら、検査の順序が違うデータができていたことになる。正を 1 か所に置いても、写しを作った時点から崩れ始めるんだよな。

# 32 ビット演算を言語ごとに合わせる

乱数は mulberry32 で、仕様には JavaScript の形で 4 行だけ書いてある。

```
a = (a + 0x6D2B79F5) | 0
t = Math.imul(a ^ (a >>> 15), 1 | a)
t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t
return (t ^ (t >>> 14)) >>> 0
```

「各演算の結果を 32 ビットに収める」という要求は同じでも、気を付ける所は言語ごとに違う。

- TypeScript：数値は倍精度の浮動小数点なので、普通の `*` では上位のビットが丸められる。掛け算は `Math.imul` に任せ、`| 0` と `>>> 0` で符号付きと符号なしを行き来する
- Java：`int` の足し算と掛け算は下位 32 ビットで折り返すので、式はほぼ写すだけで済む。`>>>` もある。落とし穴は剰余で、`int` のまま `%` を取ると負の値が出て、空きマスの選び方がずれる。値は `Integer.toUnsignedLong` で `long` に直してから剰余を取る
- Python：整数に桁の上限が無いので、放っておくと値がどこまでも大きくなる。足し算と掛け算のたびに `& 0xFFFFFFFF` を付ける。値を常に正に保っているので、`>>>` の代わりに `>>` で足りる

Python は何も折り返してくれない分、32 ビットに収める場所をすべてコードに書くことになる。仕様の「収める」がどこに効いているかが目に見えるので、参照実装としては悪くない性質かな。

ベクタの rng の節は種 0・1・42・0x6D2B79F5・0xFFFFFFFF の 5 つについて、最初の 10 個の出力を持っている。端の 0 と 0xFFFFFFFF が入っているので、符号の扱いを間違えるとここで落ちる。

# 長さを何で数えるか

手の列は 50,000 手までで、超えると too_long、U・D・L・R 以外の文字が混ざると invalid_char になる。ここで「長さ」の単位が言語によってずれる。

JavaScript と Java の `String.length` は UTF-16 のコード単位で数えるが、Python の `len` はコードポイントで数える。絵文字は UTF-16 で 2 単位なので、絵文字 25,001 個の列は JS と Java では 50,002 で too_long になる。Python の素の `len` だと 25,001 で上限の内に収まり、invalid_char になってしまう。参照実装は仕様に合わせて、`surrogatepass` で UTF-16 に符号化してから 2 で割る関数で長さを数えている。

ベクタには境目のケースを並べた。

- 絵文字 25,001 個（50,002 単位）は too_long
- 絵文字 25,000 個（50,000 単位）は上限の内なので invalid_char
- `L` を 50,000 個並べた列は too_long にならず、2 手目で盤面が動かずに no_change
- 孤立したサロゲート（対になっていない上位・下位）を含む列は invalid_char

50,001 文字のケースをそのまま JSON に書くと読めないファイルになるので、`{"repeat": "L", "count": 50001}` という生成の指示で表し、読む側で展開している。孤立したサロゲートは JSON なら `\ud83d` のエスケープで書けるので、そのままベクタに入れられる。

複数の不正が重なったときの順序も決めてある。種 → 長さ → 文字 → 再生の順で、長すぎて不正な文字も含む列は too_long になる。範囲外の種は呼び出し側の誤りなので、結果ではなく例外にしてベクタからは外した。手の列が何であっても種の例外が先に出ることは、各言語のテスト（Java は `IllegalArgumentException`、TS は `RangeError`）で個別に確かめている。

# 検査が空振りしないようにする

共通のデータを読むテストは、読み方を間違えると「0 件を検査して成功」になりうる。それを 2 つの仕掛けで止めている。

1. **ケースが 0 件のセクションは失敗にする**。TS も Java も、セクションを読む関数が空を受け取ったら失敗させる。キー名の打ち間違いや、生成で節が抜けたときに気づける
2. **version の食い違いを失敗にする**。vectors.json の先頭に形のバージョンを持たせ、テストの側にも対応するバージョンを定数で持つ。形を変えたらデータ・TS・Java の 3 か所を同時に上げる決まりで、上げ忘れるとテストが落ちる

今のセクションと件数はこうなっている。

| セクション | 件数 | 中身 |
|---|---:|---|
| rng | 5 | 種ごとの最初の 10 出力 |
| line | 14 | 1 列を左へ寄せた結果 |
| move | 12 | 盤面 3 つ × 4 方向 |
| init | 5 | 開始の盤面 |
| replay_ok | 7 | 短い局の再生（空の手の列を含む） |
| replay_full | 3 | ゲームオーバーまでの局 |
| replay_fail | 41 | 失敗のケース |

line の節は参照実装の出力だけでなく、仕様に手で計算した表も載せて突き合わせている。参照実装が間違っていたら、3 つの言語がそろって間違うことになるからね。

# 同じ形を frontmatter にも使った

この形は 2048 の前にも 1 回使っている。記事の frontmatter の解釈を、Markdown を直接読む TS 側と、API に取り込む Java 側でそろえたとき。こちらは参照実装を持たず、入力と期待する判定（記事として読む・エラー・読まない）を手で書いた JSON を両方のテストに流した。最初は 74 件で、今は 107 件ある。

# まとめ

- 正は 1 つのファイルに置き、各言語はそれを読む側に回る
- 参照実装を別の言語で書いてベクタを生成し、その参照実装も手計算の表で確かめる
- 32 ビット演算と文字列の長さは、言語ごとに落とし穴の場所が違う
- 0 件のセクションと version の食い違いは失敗にする

言語ごとに実装を分けると、仕様の曖昧な所がそのまま実装の違いとして出てくる。ベクタを作る作業は仕様の穴を先に潰す作業でもあったと思う。
