# はじめに

このブログは、もともとポートフォリオのサイト（private リポジトリ、AWS 配信）の中の 1 コーナーだった。それを別の公開リポジトリに切り離して、GitHub Pages で単独運用する形にした。この記事はその経緯と、切り離すときに決めたことを書く。

# なぜ分けたか

ポートフォリオで頻繁に更新が入るのはブログだけで、作品はそれほど増えない。それなのに、記事を 1 本足すだけで backend のテスト、インフラのデプロイ、ビルド、キャッシュ無効化まで全部の手順が回る。デプロイの重さが記事を書く腰の重さに直結していた。

目的は単純化ではなく、更新の頻度を分けることと、ブログを単独で運用できるようにすること。ポートフォリオが止まっていてもブログは動く、という形にしたかった。

# 検討した 3 案

1. **今のまま中に置く**：作り込み（デザイン、フィード、OGP、Marp 対応）がそのまま使えるが、記事のたびに全部のデプロイが回る
2. **記事だけ別リポジトリにして、本体のデプロイを起こす**：配信はポートフォリオのままで、単独運用にならない
3. **別の公開リポジトリ＋GitHub Pages で単独運用**（採用）

3 案の難点は、公開リポジトリなので下書きの扱いに気を使うことと、見た目の修正が 2 か所になること。前者はネタ帳と下書きを private 側に残して、公開するものだけをブログのリポジトリに置く運用にした。後者は、共有部品が変わったら本体のワークフローがブログ側へ PR を作る仕組みで補っている。直接 push ではなく PR なのは、公開リポジトリに出る前に中身を一度見るため。

submodule と fork は検討して外した。private を fork しても private のままで公開に変えられない。submodule は、記事のたびに本体側へ参照を進めるコミットとデプロイが要って、分けた意味がなくなる。リポジトリ間のつながりは「見た目の同期の PR」と「本体がブログの feed.xml を読んで新着を出す」の 2 本だけにしてある。

# Next.js をやめて、ビルドスクリプトにした

最初は本体の frontend（Next.js）を流用したが、ブログだけでコードが 75 ファイルあって見通しが悪い。記事を Markdown から HTML にするだけの仕事に、React のランタイムもルーティングも要らないんだよな。

なので Next.js と React を外し、TypeScript のビルドスクリプトで `out/` を吐く形に作り直した。コードは 10 ファイル前後。本体と共有するのは CSS と Markdown・Marp の変換処理だけで、HTML の構造はブログ側が自分で持つ。参考にした個人サイトが Astro 約 30 ファイルで組まれていて、「この規模ならフレームワークは要らない」と踏ん切りがついた。

テストは単体テストを置かず、ビルド時の検査だけにした。検査するのは draft の混入、未来日付、読めない記事、本文のサイズ。公開リポジトリで一番怖いのは下書きを漏らすことなので、検査はそこに集中させてある。

# 切り離しで捨てたもの

いいねとアクセス数は、ブログごと廃止した。ブログから本体の API を呼ぶと、結局ポートフォリオに依存して単独運用にならない。数字が見えなくなるのは少し寂しいが、静的サイトの身軽さのほうを取った。

URL は github.io のユーザーサイトにした。将来独自ドメインに移す可能性はあるが、サイトの URL を 1 か所の設定にまとめてあるので、ビルドし直しで移せる。

# まとめ

- 更新頻度が違うものは、リポジトリごと分けると運用が軽くなる
- public と private のつながりは最小限にし、公開側へ出る経路には人の目（PR）を挟む
- 記事を HTML にするだけなら、フレームワークは要らない。75 ファイルが 10 ファイルになった

「とりあえず本体に足す」で始めたものを切り出すのは手間だが、記事を書くたびにインフラがデプロイされる生活よりはずっといい。
