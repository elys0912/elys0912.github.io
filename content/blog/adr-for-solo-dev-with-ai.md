# はじめに

Claude Code と壁打ちしながら作っていると、決めた理由が会話ログの中に埋もれる。「なぜ WAF を入れなかったか」「なぜ Slack のセッションは普段の許可を引き継がないのか」は、決めたときの会話を読めば分かる。しかし、会話は圧縮され、セッションは閉じ、別の PC には無い。

そこで ADR（Architecture Decision Record、決定の記録）を入れた。この記事は個人開発に ADR を入れるときに何を決めたかと、過去の決定を 1 日でまとめて起こした話。

# 書く対象を 7 種類に絞る

ADR は「アーキテクチャ」の記録だが、個人開発で残したいのはそれだけではない。書く対象を 7 種類にして、front matter の `kind` に 1 つ書くことにした。

| kind | 対象 |
|---|---|
| architecture | 構成・技術選定、データの持ち方、外部サービスとの境界、セキュリティ、公開方針 |
| cost | 継続費用が発生・増減するもの、有料サービスの採否 |
| spec-change | 仕様変更と呼ぶレベルの変更 |
| feature | 機能追加 |
| bug | 致命的なバグ。原因と、どう直すと決めたか |
| design-fix | 設計ミス。何が誤りで、どう是正すると決めたか |
| improvement | 大きな改善 |

対象外は誤字や文言、軽微なバグ修正、振る舞いを変えないリファクタ、依存の定期更新。

重さは 2 段。戻すのに 1 日以上かかる、複数のリポジトリや外部サービスに影響する、公開後は変えられない、継続費用が発生する、のどれかに当たれば `full`（50〜150 行）。当たらなければ `short`（各節 1〜2 行、10〜20 行）。個人開発の決定は、3 分の 2 ほどが `short` で済んでいる。

# 決めるのは人間、と規約に書く

いちばん気にしたのはここ。Claude Code に ADR を書かせると、検討から決定まで一気に進めてしまう。「A 案と B 案を比べて A にしました」と書かれた ADR が、人間の目を通らずに accepted になりかねない。

規約に 3 つのルールを足した。

- 決めるのは人間。Claude は選択肢・良い点と悪い点・推奨を出すところまで。どれにするかは選択式の質問で選んでもらう
- 人間が選ぶ前は `proposed` のまま。選ばれた日を `approved` に書いてから `accepted` にする
- 作業中に対象になる判断が出たら、進めずに止めて質問する。既定の案で先に実装しない

3 つ目が効く。これが無いと、Claude Code は「推奨は A なので A で進めます」と言って実装を始める。止まって聞いてくるようになってから、実装を巻き戻す回数が減った。

規約の残りは公開されているものを借りた。本文に Issue や PR の番号を書かない、行番号で参照しない、進捗やチェックボックスを書かない、選択肢は 2 つ以上、結果には悪い面を必ず書く、あたり。出どころは TOKIUM の「AI に書かせた ADR を読みやすくするガイドライン」と、microsoft/hve-core の adr-author Skill。

# Skill と検査スクリプト

規約とテンプレートと検査スクリプトを、Claude Code の Skill 1 つにまとめた。Skill の中で完結させてあって、外部の台帳を参照しない。別の PC へ持っていくときに、Skill のフォルダーだけ写せば動くようにするため。

検査スクリプトは、番号の重なり、ファイル名と `id` の不一致、必須の節の欠け、選択肢が 2 つ未満、悪い面が空、置き換えの片側だけの記載、「参照」の節以外に書かれた Issue や PR の番号、`accepted` に残った「検討中」などの語、を報告する。索引の `README.md` も同じスクリプトが作り直すので、表を手で直さない。

置き場は 2 種類。private のリポジトリはそのリポジトリの `docs/adr/`。public のリポジトリはメモ用の private リポジトリの `adr/<repo 名>/`。公開リポジトリに開発用の文書を置かないという方針が先にあったので、それに合わせた。

# 過去の決定を 1 日で起こす

仕組みができたので、過去の決定を遡って書いた。対象は 17 リポジトリ。会話ログは残っていないので、材料は git の履歴、設計書、メモ、Issue と PR。

まず 1 リポジトリ（Firefox 拡張、コミット 454 件）を Claude Code と一緒にやった。候補 20 件を出させ、15 本にした。ここで分かったのは、コミットの日付だけでは決定日が取れないこと。メモとタグの日付で補った。

残り 16 リポジトリは Sonnet のサブエージェントを 2 並列にして、2 リポジトリずつ 8 回流した。起こした ADR は合計 99 本、かかった時間は 46 分。トークンは 2 並列の合計で約 116 万。

見積もりは外れた。コミット数あたりの単価で見積もったが、小さいリポジトリほど 1 リポジトリあたりが重かった。日付の裏取りで、メモと設計書と PR を横断して読むのに時間がかかっていた。小さいリポジトリでも 1 リポジトリあたり 5〜6 万トークンかかる。50 万と 91 万の時点でそれぞれ止めて、続けるか確かめた。

書き終わった ADR には、読んで「遡って書いた」と分かる記述が混じっていた。「当時は〜だった」「後から見ると」のような文。ADR は決めた時点の記録なので、遡及の記述は全部外した。

# 114 本を読んでみて

起こした ADR を索引から眺めると、同じ決定が複数のリポジトリに散らばっているのが見える。Slack 版と Discord 版の Claude Code ブリッジで「今後も許可」のルール生成を許可リスト方式にした決定は、両方に 1 本ずつある。「使用量とコンテキストを見張り、想定外の終了だけ起動し直す」も両方にある。共通化しないと決めていたので 2 本あるのは正しいのだが、同じ判断を 2 回していたことは、索引ができるまで気づかなかった。

これからは決めるたびに 1 本ずつ増える。多いか少ないかはまだ分からない。

# AI との付き合い方

規約の中身は Claude Code に案を出させて、こっちが削った。最初の案には「定期的に棚卸しする」があったが、やらないと分かっているので外した。代わりに、規約には「新しい ADR を書く前に同じ置き場の索引を読む」だけを残してある。

遡って書く作業は Claude Code に任せて正解だった。114 本を手で書く気にはならない。ただ、1 本も読まずに accepted にはしていない。決定日と選んだ案には全部目を通した。AI に書かせた ADR を AI だけでレビューして終わりにすると、規約の「決めるのは人間」が最初から崩れるんだよな。
