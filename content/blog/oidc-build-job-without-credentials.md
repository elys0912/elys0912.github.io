# はじめに

ポートフォリオのサイトは GitHub Actions から OIDC で AWS のロールを引き受けてデプロイしている。長期のアクセスキーは置かず、`id-token: write` は AWS に公開するジョブにだけ付け、ジョブごとにテストで検査している。[前に書いた記事](/posts/github-actions-oidc-deploy/)のとおり。

その「デプロイのジョブ」の中で、frontend の `npm ci` と `next build` が AWS の認証の後に動いていた。Issue に積んだままだったのを、今週直した。直し方は Claude Code と壁打ちした。どこまでを別のジョブにするかは、こっちで決めた。

# 何がまずいか

ジョブの流れはこうだった。

1. backend を Maven でビルドしてテスト
2. OIDC でロールを引き受ける
3. CDK でスタックをデプロイし、出力をファイルに書く
4. 出力からサイトの URL を読み、frontend を `npm ci` して `next build`
5. S3 へ sync して CloudFront の invalidation

手順 4 が問題。frontend の依存のどれかが侵害されると、インストール時のスクリプトやビルド時に動くコードが、環境変数にある 1 時間有効な AWS の資格情報を外へ送れる。frontend の依存は Dependabot が月 1 回まとめて更新するので、入れ替わりが多い。侵害を防ぐことはできないが、侵害されたコードが資格情報に届かないようにはできる。

# 順序を変えるだけでは足りない

最初に思いつくのは、同じジョブの中でビルドを認証より前に移すこと。ジョブは増えないし分数も変わらない。

ただ、これだとジョブに `id-token: write` が残る。OIDC のトークンは `ACTIONS_ID_TOKEN_REQUEST_TOKEN` と URL が環境変数にあれば、ジョブの中のどのステップからでも取れる。依存のコードがトークンを取ってロールを引き受ける経路が残る。認証の前に動かしても守れていない。ここは Claude Code に指摘されるまで気づいていなかった。

そこで、ジョブの権限で分けた。

- frontend の `npm ci`・lint・テスト・ビルドは、`id-token` を持たない別のジョブで行う
- ビルドの結果（静的ファイル）だけを artifact で公開のジョブへ渡す。保持は 1 日
- OIDC のトークンを取れるジョブは、frontend の依存を入れず、frontend のコードも動かさない

手順の並び順に頼らず、権限で守る形。

# サイトの URL を認証なしで作る

ビルドにはサイトの URL が必要。OGP の `og:url` と canonical に入れるため。これまではスタックのデプロイの出力から読んでいたが、ビルドを認証の前に置くと出力が無い。

リポジトリの Variables に置く案は捨てた。スタックの出力と二重の管理になるし、手で登録する項目が増える。代わりに、認証なしで読める `infra/cdk.json` の `domainName` から組み立てることにした。スタックの出力の SiteUrl も、元はこの値から作っている。出どころが同じなら食い違わない。

独自ドメインを外して CloudFront のドメイン名で公開する構成に戻すときは、この方法が使えない。そのときは渡し方を決め直す。悪い面として ADR に書いておいた。

# backend は残した

backend のビルド（Maven）と infra のテスト（npm）は OIDC のジョブに残した。

backend も別のジョブにすれば、残る経路は infra の依存だけになる。とはいえ、Lambda の zip も artifact で渡すことになり、実際のデプロイでしか確かめられない箇所が増える。入れ替わりが多く数も多いのは frontend の依存で、ここを切り離すのがいちばん効く。backend と infra の依存が侵害されたときの経路は残る。これも ADR に書いた。

ジョブを分けると費用も増える。GitHub Actions の private リポジトリの分数は、ジョブごとに分単位で切り上げられるので、ジョブが 1 つ増えるぶん 1 回あたりの分数が増える。毎日動く定期ビルドのほうが、月の無料枠に対する増え方は大きくなるはず。

# 直した日に、原稿が公開されなかった

ここからが本題。

直した当日、作品のページを 1 つ足してマージした。デプロイは成功。しかし、サイトにそのページが出ない。

frontend のビルドは、作品の記事を API から取って静的なページにする。記事は、スタックのデプロイのときに migration がリポジトリの原稿から DB へ入れる。今回の変更で、ビルドを OIDC のジョブの前に置いた。つまり、ビルドがスタックのデプロイより前に動くようになった。原稿の変更は DB に入る前にビルドされ、そのデプロイでは公開されない。次のビルド（次のデプロイか翌日の定期ビルド）まで遅れる。

決めたときに、ビルドが DB の中身に頼ることを見落としていた。順序を入れ替えるなら、データの依存を先に洗うべきだった。ワークフローは成功と表示されていたので、ページを見に行かなければ気づかなかった。

# 4 つのジョブにする

直し方の候補は 3 つあった。

- スタックをデプロイした回だけ、最後に定期ビルドを起動する。変更は小さいが、古い内容が一度公開されてから作り直され、ビルドと公開が 2 回走る
- ジョブの分離をやめて 1 つに戻す。順序は元に戻るが、依存のコードが資格情報の下で動く状態に戻る
- このままにして、原稿の変更は次のビルドで公開されるものとする。マージしても公開されない時間が最長で 1 日近く残る

どれも採らず、ジョブを 4 つにした。検査（何をデプロイするかの判定と frontend のテスト）、スタックのデプロイ、ビルド、公開の順。検査とビルドには `id-token` を渡さない。スタックのデプロイと公開だけが OIDC でロールを引き受ける。スタックのデプロイが要らない回はそのジョブを飛ばしてビルドと公開へ進み、失敗した回はビルドも公開もしない。

元の順序（検査、スタックのデプロイ、ビルド、公開）と、依存のコードを資格情報から切り離すことの両方を守れるのは、挙がった案の中ではこの形だけだった。

悪い面は、ジョブが 2 つから 4 つになって 1 回あたりの分数が 2 分ほど増えること。frontend の依存を入れる処理が、検査（テストを省かない回）とビルドの 2 回になること。飛ばされたジョブの後ろを動かす `if` の書き方が増えて、ワークフローが読みにくくなること。条件はテストで確かめている。

# AI との付き合い方

「同じジョブの中で順序を変えるだけでは守れない」は Claude Code の指摘で、こっちの見落とし。「ビルドが DB に頼っているから順序を変えると壊れる」は、Claude Code も見落とした。前者は OIDC の仕組みの知識で、後者はポートフォリオのサイトの構成の知識。AI が知らないのは後者のほうなんだよな。

構成の知識は ADR に残すことにした。今回の 2 本（ジョブの分離と、4 つのジョブへの直し）も、選んだ案と捨てた案と悪い面を書いてある。次に順序を触るときに、Claude Code が先に読める形で。
