# はじめに

claude-slack-channel と claude-discord-channel は、チャットから手元の Claude Code を動かすためのブリッジ。起動スクリプトが `claude.exe` を隠しウィンドウで立ち上げ、チャットのメッセージを MCP 経由でセッションに渡している。手元の画面には何も出ていない。

この形だと、セッションが止まっても誰も気づかない。チャットからは、届いた印の 👀 が付いたまま何も返ってこないようにしか見えない。エラーで落ちるなら hook で知らせられるが、止まる原因の多くはエラーではなかった。

前に書いた[Windows のコンソールを外から操作する](/posts/driving-windows-console-from-outside/)の続きとして、その原因を 4 つ書く。原因の見当は AI と壁打ちしながら絞ったが、どれも実機で起きてはじめて分かったものだった。

# 1. 許可依頼ではない選択画面（2026-09-30）

Slack から頼んだ作業で、Claude がブラウザを操作するスキル（claude-in-chrome）を呼んだ。するとターミナルに「Claude wants to use your browser」という選択画面が出て、そこで止まった。

ブリッジは Claude Code の実行許可の依頼（permission request）を Slack のボタンに中継している。ただし中継できるのは、実行許可として飛んでくるものだけ。この選択画面は実行許可ではないので、Slack には何も来ない。隠しウィンドウの中で、選択を待ったまま止まっていた。

対処は起動の引数に `--no-chrome` を足すこと。チャットから使うセッションでブラウザを動かす場面は無いので、機能ごと切った。

厄介なのは、同じ形の画面がほかにもありうること。実行許可ではない確認や選択は、Claude Code のバージョンが上がるたびに増えるかもしれない。1 つずつ切っていくのでは追いつかないので、この日のうちに見張りを 2 つ足している。

- 最後に渡したメッセージから 5 分、Claude が reply も react も呼ばなければ、そのスレッドに警告を出す
- `!screen` でターミナルの画面を読み、選択画面なら選択肢をボタンにして返す

止まる原因を全部潰すのは無理なので、止まったことに気づける形と、チャットから外せる形を先に作った。`!screen` の中身は前の記事に書いた。

# 2. 親のセッションの環境変数（2026-09-30）

起動スクリプトを、Claude Code のセッションの中（VS Code の拡張など）から実行したときだけ、Slack に返事が来なかった。

調べると、親のセッションの目印になる環境変数が、起動した `claude.exe` に引き継がれていた。`CLAUDECODE`、`CLAUDE_CODE_CHILD_SESSION`、`MCP_CONNECTION_NONBLOCKING` などで、これがあると起動したセッションが子のセッションとして扱われる。会話が保存されず、MCP の接続も非同期になって、ブリッジの reply ツールが使えなかった。メッセージは届いても、返す手段が無い。

起動スクリプトで、`claude.exe` を起動する前にこれらを消すようにした。

```powershell
@(
    'CLAUDECODE', 'CLAUDE_PID', 'CLAUDE_AGENT_SDK_VERSION', 'MCP_CONNECTION_NONBLOCKING',
    'CLAUDE_CODE_CHILD_SESSION', 'CLAUDE_CODE_ENTRYPOINT', 'CLAUDE_CODE_SESSION_ID',
    'CLAUDE_CODE_SESSION_ATTENDED', 'CLAUDE_CODE_MESSAGING_SOCKET',
    'CLAUDE_CODE_ENABLE_SDK_FILE_CHECKPOINTING', 'CLAUDE_CODE_ENABLE_TASKS'
) | ForEach-Object { Remove-Item -Path "Env:$_" -ErrorAction SilentlyContinue }
```

どれも Claude Code の内部の目印なので、バージョンが上がれば名前が増えたり変わったりするかもしれない。

手元のターミナルから起動するときは踏まない。Claude Code のセッションの中から起動したときだけ踏む。AI に作業を任せる前提の道具ほど、AI のセッションの中から動かされることを考えておく必要があるわけだ。

# 3. 起動直後の入力例（2026-10-03）

ここからの 2 つは、セッションそのものではなく、止まったときに立て直すためのコマンドが止まる話。

`!restart` と `!compact` はターミナルの入力欄に `/exit` や `/compact` を打ち込む。打ちかけの文字を壊さないように、入力欄が空のときだけ送る作りにしてある。

ところが、起動した直後の `!restart` が「入力待ちでない」と断り続けた。画面を読むと、入力欄に薄く入力例が出ている。

```text
> Try "how do I log an error?"
```

ブリッジは画面を `ReadConsoleOutputCharacter` で文字として読んでいるので、薄い表示かどうかは分からない。入力例も打ちかけの文字に見えていた。ちなみに、記号の後ろの空白はノーブレークスペースになっている。

入力例だけの行に限って、空の入力欄とみなすようにした。

```ts
const EMPTY_PROMPT_RE = /^\s*[❯>](?:\s*|[\s\u00a0]+Try "[^"]*")$/;
```

`Try "…"` の後ろに続きがあれば、今までどおり打ちかけとして扱う。テストには実機の `!screen` で取れた画面の末尾をそのまま入れてある。

# 4. 応答のあとの入力の候補（2026-10-14）

3 と同じ形の問題が 11 日後にもう一度出た。今度は `!clear`・`!compact`・`!restart` が止まる。

Claude Code は応答のあと、次に打ちそうな文を入力欄に薄く出す（prompt suggestions）。これも文字で読むと、打ちかけの文字と見分けがつかない。候補の文面は応答ごとに変わるので、入力例のように決まった形で拾うのも難しい。

こちらは判定を緩めるのをやめて、候補の表示そのものを切った。チャット用のセッションだけが読む設定ファイルに 1 行足している。

```json
"promptSuggestionEnabled": false
```

セッションは `--setting-sources project,local` で起動しているので、手元で使う普段の Claude Code の設定には影響しない。Slack 版と Discord 版の両方に、同じ夜に入れた。

画面の色（属性）まで読めば、薄い表示を見分けられるのかもしれない。ただ、試してはいない。表示を消せるなら、読み方を賢くするより確実だと考えた。

# 共通していること

4 つを並べると、止まり方は 2 種類ある。

| 原因 | 止まるもの | チャットからの見え方 |
|---|---|---|
| 許可依頼ではない選択画面 | セッション | 👀 のまま返事が無い |
| 親のセッションの環境変数 | 返事の経路 | 👀 のまま返事が無い |
| 起動直後の入力例 | 立て直しのコマンド | 「入力待ちでない」と断られる |
| 応答のあとの入力の候補 | 立て直しのコマンド | 同上 |

前の 2 つは、ブリッジの外で起きる。Claude Code の画面や環境のことを、ブリッジは知らない。後ろの 2 つは、ブリッジが画面を文字でしか読めないことから来ている。人の目には薄い文字と分かるものが、ブリッジには打ちかけの文字に見えた。

どれも、手元で Claude Code を使っているときは問題にならない。選択画面が出れば押すし、入力例が薄いのは見れば分かる。外から使うと、人が見ていれば済んでいたところが全部抜けて、そこで止まる。

このほかに、Claude Code 2.1.289 でチャンネル自体が無効になった件もあった。こちらは前の記事に書いた。

# まとめ

- 実行許可ではない選択画面は、チャットに中継されない。使わない機能は起動の引数で切る
- Claude Code の中から起動すると、親の環境変数で子のセッションになる。起動前に消す
- 画面を文字で読むと、薄い表示と打ちかけの文字を見分けられない。決まった形なら判定で拾い、毎回変わるなら表示を切る
- 原因を全部潰すのは無理なので、止まったことに気づく見張りと、チャットから外す手段を先に用意する

experimental の機能の上に乗っている以上、5 つ目もそのうち来る。来たら、見張りが鳴ってくれるのを期待している。
