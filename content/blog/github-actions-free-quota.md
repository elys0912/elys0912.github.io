# はじめに

2026-10-10 に GitHub から「Actions storage 100%」のメールが来た。12 日から 13 日にかけて PR の CI で gitleaks が `Artifact storage quota has been hit` で落ちた。調べると、分数のほうも月末に無料枠を超えるペースだった。

使っているのは GitHub Free。このサイトのリポジトリは private なので、無料枠の中で動かしている。調べたことと、減らすためにやったことを書く。

作業は AI（Claude Code）と壁打ちしながら進めた。どの案を採るかはこっちで決めている。

# 無料枠の数え方

GitHub Free の private リポジトリでは、次の枠がある。public のリポジトリは、分数もストレージも数えない。

| 項目 | 枠 | 数え方 |
|---|---|---|
| 分数 | 月 2,000 分 | Linux は 1 倍、Windows は 2 倍。ジョブごとに分単位で切り上げ |
| ストレージ（Artifact と Packages） | 0.5GB | 月の累積（GB 時）。0.5GB × 744 時間で、月に約 372 GB 時 |
| キャッシュ | リポジトリごとに 10GB | 上の 0.5GB とは別枠。7 日使われなければ消える |

勘違いしていたのはストレージ。0.5GB を「置いておける容量」だと思っていたが、実際は「置いた量 × 置いた時間」を月の間ずっと足していく。だから、気づいて消しても、それまでに数えた分は戻らない。月の途中で使い切ったら、その月はもう終わりになる。

# 何が枠を食っていたか

10/1〜10/12 の使用量はこうだった。

| 項目 | 使用量 | 枠 |
|---|---|---|
| Linux | 約 950 分 | 2,000 分 |
| Windows | 78 分（2 倍で 156 分ぶん） | 同上 |
| Actions storage | 372 GB 時 | 約 372 GB 時（使い切り） |

## ストレージ

原因は CI が Artifact に上げていた `backend-lambda.zip`（約 60MB、保持 3 日）だった。10/7〜10/9 に PR が多く、そのたびに上がっていた。どこからも使われていない。デプロイは自分で zip を作り直すので、CI の zip を誰も取りに来ていなかった。

キャッシュも同じ時期に 7GB を超えるまで増えていて、最初はこっちを疑った。実は、キャッシュは別枠で、0.5GB には数えない。キャッシュを消すワークフローを足しても枠切れの対策にはならず、private では掃除そのものが分数を食う。数え方を確かめずに手を打っていたら、効かない対策を足すところだった。

枠を使い切ったときの挙動も分かった。予算が $0 なので課金はされず、Artifact のアップロードが失敗してジョブが落ちる。gitleaks の SARIF を Artifact に上げていたので、そこで落ちた。

## 分数

分数は 12 日の時点で枠の半分を使っていた。月の 4 割の時点なので、月末には 500 分前後の超過になる見込みだった。超過の単価は Linux で 1 分 $0.006 なので、超えても月 $3 程度。お金の問題ではなく、予算が $0 なので、超えた時点で Deploy が動かなくなるほうが困る。

内訳を見ると、1 件の変更で走るものが多い。PR に push するたびに CI と Security（gitleaks）が走り、マージすると CI・Deploy・Sync shared to blog が走る。マージ 1 回で 7〜11 分になる。

| ワークフロー | 回数 | 1 回あたり |
|---|---|---|
| Deploy | 64 回 | 約 4.8 分 |
| CI | 139 回 | 1〜4.6 分 |
| Security（gitleaks） | 77 回 | 1 分（実行は 10 秒） |
| Sync shared to blog | 25 回 | 1 分 |
| Dependabot の更新 | 21 回 | 約 2 分 |

地味に効いているのが切り上げ。gitleaks は 10 秒で終わるのに、1 回 1 分で数える。短いジョブを別々に走らせると、そのたびに 1 分ずつ取られる。

もう 1 つは、Claude のセッションが 1 つの PR に何度も push すること。push のたびに CI と Security が回る。AI と作ると、ここは人間だけのときより増える。

# やったこと

| 対策 | 効く先 |
|---|---|
| `backend-lambda.zip` と gitleaks の SARIF を Artifact に上げない | ストレージ |
| Artifact とログの保持期間を 90 日から 7 日に縮める（private の全リポジトリ） | ストレージ |
| Deploy を README・docs・ほかのワークフローだけの変更では動かさない。frontend だけの変更なら `cdk deploy` を飛ばす | 分数 |
| gitleaks を CI の 1 ステップに入れる（週 1 回の定期実行は残す） | 分数 |
| Sync shared to blog を `frontend/**` の push だけで動かす | 分数 |
| Dependabot を月 1 回にし、minor と patch を 1 つの PR にまとめる | 分数 |
| CI を PR だけ・1 ジョブにする。デプロイの backend のテストは、マージ元の PR の CI が通っていれば省く | 分数 |
| Windows の CI があったリポジトリ（claude-discord-channel）を public にする | 分数 |

Deploy の起動条件を絞るところは注意が要った。記事の content を変えたときは、API のスタックのデプロイが要る（記事を DB に入れる Lambda がそこで動く）。判定を間違えると、記事が DB に入らないまま Deploy が成功する。

public にしたリポジトリは、公開前にテストに入っていた実際の ID をダミーに置き換えた。

# やらなかったこと

- **予算を付けて止まらないようにする**：$2 くらいの予算を付ければ、超えても Deploy は止まらない。とはいえ、超えそうなら使い方を直すほうが先なので、予算は $0 のままにした
- **キャッシュを消すワークフロー**：上に書いたとおり、ストレージの枠には効かない。必要になったら、PR を閉じたときにそのブランチのキャッシュだけ消す形を考える
- **テストを減らす**：Deploy の前のテストは main を守る最後の砦なので、CI で代わりができたところだけ省いた

# これから

いちばん効くのは public にすること。public のリポジトリは標準ランナーの分数もストレージも数えない。公開前のチェックがまだ残っているので、どこまで早められるかは考え中。

もう 1 つは self-hosted runner。手元の PC で CI を動かせば分数は使わない。もっとも、PC が止まっていると CI も止まるし、public のリポジトリに付けるとフォークからの PR で任意のコードが手元で動く。付けるなら private のリポジトリの CI だけにする。

# まとめ

- ストレージの枠は「置いた量 × 時間」の月の累積。消しても戻らない
- キャッシュは別枠。枠切れの対策にはならない
- 短いジョブは 1 回 1 分に切り上がる。まとめるだけで減る
- 誰も取りに来ない Artifact は上げない

月 $3 の話なので、お金だけなら放っておいてもよかった。ただ、無料枠で止まる設定にしていると、枠切れはそのままデプロイの停止になる。何が枠を食っているかは、一度見ておくとええ。
