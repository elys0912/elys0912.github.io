# はじめに

サイトの 2048 にランキングを付けたとき、API の前に AWS WAF を置くかで迷った。結論は入れない。代わりに API Gateway のスロットル（毎秒の上限）を下げ、叩かれ続けたときに払う額の上限を先に計算しておく形にした。

AWS Budgets の通知は $1 で鳴るようにしてある。この記事はその $1 を基準に何を比べて何を捨てたかを書く。検討とレビューは AI（Claude Code）と壁打ちしながら進め、どれを採るかはこっちで決めた。金額は東京リージョンの単価で、税抜き。

# 構成ごとの月額

想定は、API の呼び出しが月 5 万回、CloudFront が月 10 万リクエスト。独自ドメインのホストゾーンが固定で $0.50 かかり、税を足すと約 $0.55 になる。$1 の通知までの余裕は約 $0.45 しかない。

| 構成 | 月額 | 中身 |
|---|---|---|
| A：WAF なし | $0.06〜$1.56 | API Gateway が約 $0.06。DSQL は 1 回あたりの使用量の仮定しだいで $0〜$1.50。監視とログは無料枠の内 |
| B：A ＋ WAF | $6.12〜$7.62 | Web ACL $5 ＋ ルール $1 ＋ $0.60／100 万リクエスト |
| C：A ＋ 外形監視（5 分おき） | $16.3〜$17.8 ＋ 付随の費用 | 1 回 $0.0019 × 月 8,640 回 |

WAF は、ルールを 1 本しか置かなくても固定で $6 が乗る。これだけで $1 の予算の 6 倍になる。外形監視も同じ理由で外し、毎日の再ビルドが API から記事を取る処理の失敗メールで代わりにしている。

CloudFront の定額プラン（Free）には、IP ごとのレート制限を含む WAF が付いていて、超過の課金も無い。使えれば一番いいが、今の構成のままでは切り替えられない。独自のレスポンスヘッダーのポリシーや価格クラスの指定を外す必要があり、アカウントの種類によっては対象外になるかもしれない。調べてはみたが、切り替えるかどうかはまだ決めていない。このアカウントは、CLI ではプランを判定できなかったものの、作成日が新しい無料プランの始まる前だったので、対象外にはならない見込みだ。それでも切り替えには中規模の作業が要るので、当面は今の構成のまま運用している。

# 叩かれたときの上限を先に計算する

WAF を入れないなら、何が上限になるのかを数字で持っておきたい。今の構成では、API Gateway のスロットルがそれにあたる。上限を超えたリクエストは API Gateway が 429 で返すので、Lambda も DB も動かない。

ここで効いたのが、AI に頼んだコストのレビューだった。2 つのモデルに互いの結果を見せずにレビューさせたら、片方が「スロットルの上限まで叩かれ続けたら月いくらか」を計算してきた。当時は記事のルートが毎秒 10、ゲームのルートが毎秒 5 で、合わせて毎秒 15 回。1 か月続くと約 3,888 万回になる。1 回 50 ms・メモリ 1 GB と仮定すると、内訳はこうなる。

- API Gateway 約 $50
- Lambda の要求と実行時間 約 $28
- ログ 約 $11
- CloudFront を経由する分 約 $35

合わせて月 $89〜124。もう片方のモデルは、想定の月 5 万回で無料枠の内に収まることを確かめただけで、上限の側は計算していなかった。想定の側だけ見ていると、この数字は出てこないね。

しかも記事のルートを使うのは、毎日の再ビルドとデプロイのときのビルドだけだった。サイトは静的に書き出しているので、利用者のブラウザは記事の API を呼ばない。ビルドのためだけに毎秒 10 回の枠を開けておく理由は無い。

# 毎秒 3・バースト 6 に下げる

決めたのは 2 つ。

1. 記事のルートを毎秒 3、バースト 6 に下げる。ゲームのルートは毎秒 5、バースト 10 のまま
2. その前に、ビルド側の記事の取得に、429 と 5xx の再試行を入れる。3 回まで、1・2・4 秒あけて取り直す。`Retry-After` が返ればそれに従い、長くても 10 秒で打ち切る

先にやるのは 2。スロットルは接続元ごとではなく全員で 1 つの枠を共有するので、誰かに枠を使い切られると、その間のビルドも 429 を受ける。再試行が無いまま枠を絞ると、ビルドのほうが先に落ちる。取り直しても取り切れなかったらビルドは失敗し、サイトは前回の公開のまま残る。それで困ることは無い。

毎秒 3・バースト 6 と低めにしたのは、記事のルートを使うのがビルドだけで、429 を受けてもビルド側の再試行で吸収できるから。

下げた後の上限は次のとおり。

| 叩かれ方 | 月の上限（推定） |
|---|---|
| 両方のルートを上限まで（合わせて毎秒 8） | $55 前後 |
| 記事のルートだけ（毎秒 3） | $11 前後 |

$89〜124 から半分ほどになった。ゼロにはならないが、「最悪でいくら」が分かっていると、WAF の固定費と同じ土俵で比べられる。

# 気づいて止める

上限があっても、1 か月放っておく前提ではない。API 全体のリクエストが 1 時間で 500 件を超えたら、アラームが鳴る。公開から 1 か月の実測で、1 時間の最大は 54 件だった。その約 9 倍にあたる。最初は 3,000 件にしていたが、実測を見て下げた。

アラームが鳴ると、Lambda が記事とゲームの両方のルートのスロットルを自動で 0 にする。夜中に鳴っても、気づくのを待たずに数分で止まる。戻すのは手でやる。

鳴ったときにゲームの API を止める手順は、README に書いてある。

1. ゲームのルートのスロットルを 0 にする。デプロイを待たずに効き、API Gateway が 429 を返すので、Lambda と DB には届かない
2. 機能フラグ（`gamesEnabled`）を false にした PR をマージする。デプロイの後、ゲームの API は 404 を返し、画面も消える

1 だけで済ませないのは、これがテンプレートの外での変更だから。スタックが更新されると、コードに書いた値（毎秒 5）に戻る。いつ戻るかに頼らないよう、2 と組にしている。Lambda の環境変数を変える手は効かない。API Gateway が呼ぶのは公開済みのバージョンなので、`$LATEST` の環境変数は使われない。0 で本当に全部を断れるかは、本番を止めずに確かめた。同じ設定の使い捨ての API を作って 0 を入れると、どちらのルートも 429 を返し、戻すと元に戻った。

# 残したリスク

- スロットルは全員で 1 つの枠なので、ランキングの取得を連打されると、普通に遊んでいる人も 429 になりうる
- アラームは無料枠の 10 本に収める。同じアカウントに別の作品のアラームが増えると枠を超えるので、本数は作品をまたいで数えている
- Budgets は通知であって、$1 で止まるわけではない。Budgets のアクションで自動で止める手も調べたが、使わないことにした

Budgets のアクションで選べるのは、IAM ポリシーや SCP の適用と、EC2・RDS のインスタンスの停止だけ。CloudFront や API Gateway の配信は止められない。IAM で拒否しても、閲覧者からのリクエストには効かない。そのうえ Budgets の情報は 8〜24 時間遅れで更新されるので、仮に止められたとしても間に合わない。自動で止めるなら、アラームからスロットルを 0 にする仕組みを作るしかない。DSQL の使用量を測ってみると 1 回あたり約 0.1 DPU で、上限まで 1 か月叩かれても全体で月 $75 前後と出た。夜中に気づけないほうが怖かったので、作ることにした。

# まとめ

- WAF は固定で月 $6 かかり、$1 の予算に収まらないので入れない
- 代わりに、スロットルの上限まで叩かれたときの月額を先に計算する
- 使うのがビルドだけのルートは絞る。絞る前に、ビルド側に再試行を入れる
- アラームで自動でスロットルを 0 にし、機能フラグで本式に止める

防御を足せば費用が増え、費用を抑えれば防御が薄くなる。どこで釣り合わせるかは最悪の月額を数字で持っていないと決められないんだよな。
