# はじめに

ポートフォリオのサイトのフロントは Next.js 16 で、`output: 'export'` の静的 export にして S3 と CloudFront で配っている。2026-10-09 に、ゲーム（2048）を通しで確かめていたところ、ブラウザの開発者ツールに 404 が並んでいるのに気づいた。

結論から書くと、Windows でビルドしたときだけ起きる Next.js の既知の問題だった。本番は Linux でビルドしているので出ない。それでも手元のために直したので、調べた順に書いておく。調べ物と修正は AI（Claude Code）と壁打ちしながら進めた。

# 事象

404 になっていたのは、`<Link>` の先読み（prefetch）の要求だった。Next.js の `<Link>` は画面に入ったリンクの遷移先のデータを先に取りに行く。静的 export では、そのデータは `__next.` で始まる `.txt` のファイルとして書き出される。

例えば `/about/` へのリンクなら、クライアントはこれを取りに行く。

```
/about/__next.about.__PAGE__.txt
```

ところが、書き出されたファイルはこうなっていた。

```
about/__next.about/__PAGE__.txt
```

名前の途中の `.` が `/` になって、サブディレクトリに入っている。ゲームのページに限らず、`/`、`/about/`、`/works/` でも同じだった。確かめたのは手元の静的配信で、最初は Next.js 16 の静的 export と `trailingSlash: true` の組み合わせを疑っていた。本番でも出るはずだと思い込んでいたが、これは確かめていなかった。

# 原因：path.relative の「\」

Next.js の中を読むと、書き出す側と取りに行く側で、ファイル名の作り方が食い違っていた。

- 取りに行く側（クライアント）は、セグメントのパス（`/about/__PAGE__` のようなもの）の区切りの `/` を `.` に置き換えて、ファイル名にする（`segment-value-encoding.js` の `convertSegmentPathToStaticExportFilename`）
- 書き出す側（`next/dist/export/index.js`）は、セグメントのパスを `path.relative` で作る

`path.relative` は OS の区切り文字を使う。Linux なら `/` で、置き換えの対象になる。Windows では `\` になるので、`/` を `.` にする置き換えに引っかからない。そのまま `path.join` に渡ると、`\` はディレクトリの区切りとして扱われ、サブディレクトリが作られる。

つまり、Windows でビルドした `out/` だけが、クライアントの期待と違う形になる。Linux でビルドすれば、名前は一致する。

調べると、vercel/next.js#85374 として報告済みだった。題名は「Next.js >=16.0.0: Mismatch in RSC file paths causes 404 errors in static exports on Windows」。2025-10 から open のままになっている。後処理のコードのコメントには、16.3.8、16.4.0、16.5.0-canary.5 でも同じだと残してある。

本番の Deploy は GitHub Actions の ubuntu の runner でビルドしているので、本番では先読みに 200 が返っている。最初に心配した「本番でも出る」は外れていた。

開発環境を WSL2 から Windows ネイティブに移したのが、ちょうど同じ 10/9 だった（[移行の記事](/posts/wsl2-to-windows-native/)）。WSL2 でビルドしていた頃は Linux なので出ておらず、移した日に初めて踏んだ。

# 直すか、直さないか

本番に影響が無いので、放っておく手もあった。選択肢は 3 つ。

1. 直さない。本番は Linux でビルドするので出ない
2. Next.js の修正を待つ
3. ビルドの後処理で、ファイルを正しい名前に移す

選んだのは 3。手元で確かめるたびに 404 が並ぶと、本物の不具合と見分けにくい。後処理なら、Linux のビルドでは移すものが無いので何もしないし、Next.js 側で直った後も何もしない。

# 直し方：postbuild で移す

ポートフォリオのサイトはもともと `next build` の後に `scripts/postbuild.mjs` を走らせている（サイトマップや画像の後始末）。そこに 1 段足した。

やっていることは単純。

- `out/` の下を走査し、名前が `__next.` で始まるディレクトリを探す
- その中のファイルを、パスの区切りを `.` にした名前で、ディレクトリの隣へ移す（`about/__next.about/__PAGE__.txt` → `about/__next.about.__PAGE__.txt`）
- 移し終わって空になったディレクトリを消す
- 移し先に同じ名前のファイルが既にあれば、上書きせずに失敗させる
- 移したものがあれば、件数と issue の番号を警告に出す

ゲームの機能フラグが無効なときは `out/games/` を取り除く処理があるので、それより後に動かしている。取り除くページの分まで移さないため。

気にしたのは、Next.js の内部の規則に乗っかっていること。ファイル名の規則がバージョンアップで変われば、この後処理は気づかないうちに的外れになる。そこでテストでは、Next.js のクライアントが使う関数（`convertSegmentPathToStaticExportFilename`）を直接 import して、移した後の名前がその関数の出力と一致するかを突き合わせている。`/about/__PAGE__` のような普通のページに加えて、`/works/$d$slug/__PAGE__` のような動的ルートや `/_not-found` も入れた。規則や関数の場所が変われば、テストが落ちて気づける。

この修正は見つけた日のうちに main に入れた。

# 別件：CSS の preload の警告

同じ確認で、もう 1 つ警告が出ていた。「preload した CSS が数秒以内に使われていない」というもの。

こちらは Windows に関係なく、本番でもモバイルでも出る。先読みの応答に、遷移先の CSS を先に読む指示が入っていて、遷移しないうちはその CSS が使われないために出るようだ。vercel/next.js#51524（「Preloaded CSS files not used within a few seconds」）として長く open のままになっている。

実害は警告だけ。直すには先読みそのものを止めるか、Next.js の内部の形式に頼るしかない。なので、こちらは Next.js の修正を待つことにした。

# まとめ

- Next.js 16 の静的 export を Windows でビルドすると、先読みのファイルがサブディレクトリに書き出され、クライアントの要求が 404 になる（vercel/next.js#85374）
- 原因は、書き出す側が `path.relative` の `\` 区切りを `.` に置き換えないこと。Linux のビルドでは起きない
- 本番は Linux でビルドするので影響なし。手元のために postbuild で正しい名前へ移し、Next.js の関数と突き合わせるテストで規則の変化に備えた
- CSS の preload の警告（vercel/next.js#51524）は別件。実害は警告だけなので待つ

OS の区切り文字の違いは Node.js で書いたツールの定番の落とし穴。とはいえ、書いたコードではなくフレームワークの中で踏むと、まず手元の設定を疑ってしまうからね。「本番でも出るはず」と思い込む前に、どこでビルドしたものかを見るのが早かった。
