# はじめに

量のある検証作業を、複数の Claude Code セッションに分担させて回した。1 つのセッションをオーケストレーター（指揮役）にして、残りを作業役にする形。人間は指揮役とだけやり取りする。

やってみると、うまく回る型と、静かに壊れる型がはっきり分かれた。題材の中身は書けないので、回し方の型だけを書く。

# 役割を分ける

- **指揮役**：作業の割り当て、報告の受け取り、人間への確認。自分では作業しない
- **作業役**：割り当てられた範囲だけをやる。判断に迷ったら指揮役に聞く

判断と承認は指揮役から降ろす形に固定した。作業役が人間に直接「これでいいですか」と聞き始めると、人間が複数のセッションの文脈を全部持つことになって、分担した意味がなくなる。作業役は「割り当ては承認済みのもの」として扱い、例外だけが指揮役経由で上がってくる。

# うまく回った型

## 常に 2 つ以上を動かす

1 本の作業が終わるのを待ってから次を切るのではなく、前工程を切り出して並行させる。片方が重い処理で止まっている間も、もう片方は進んでいる。人間側の待ち時間がほぼ消える。

ただし並列は 2〜3 本まで。それ以上に増やすと、指揮役が報告をさばく時間のほうが長くなる。あと、同じファイルに触る修正を別の束に割ると衝突するので、束はファイルが重ならない単位で切る。

## 報告は検証できる形で受ける

「終わりました」だけの報告は受けない。どのファイルのどの位置を変えたか、コミットの sha は何か、まで付けさせる。指揮役はそれを突き合わせてから次を割り当てる。

これを決めたのは、自己申告と実物がずれた経験があるから。自己申告のチェックリストと、別のセッションによるレビューの両方をかけたら、出てきた問題の大半は片方でしか見つからなかった。自己申告とレビューは代替にならず、両方要る。

## 留保は留保ごと伝える

作業役が「おそらく A だが、B の可能性も残る」と報告してきたとき、指揮役が「A とのことです」と留保を落として転送すると、そこから誤判定が生まれる。伝言ゲームで断定に化けるのは人間の組織と同じで、留保付きの回答は留保ごと運ぶのをルールにした。

# 失敗は作業側ではなく指示側にあった

一番の学びはこれ。作業役の出力がおかしいとき、原因をたどると大半は指示が悪かった。範囲が曖昧、前提を渡していない、判断基準を決めずに投げている。作業役は渡されたものに対しては素直に動くので、変な結果は変な指示の鏡になってる。

人間がチームで仕事をするときの教訓がそのまま当てはまるのは、わかってみれば当たり前なんだけど、AI 相手だと「いい感じに察してくれる」ことをつい期待してしまうんだよな。察しに頼った分だけ、後で検証の手間になって返ってくる。

# まとめ

- 判断の経路は 1 本にする。人間は指揮役とだけ話す
- 並列は 2〜3 本、ファイルが重ならない単位で切る
- 報告は検証できる形（ファイル・位置・sha）で受ける
- 自己申告とレビューは両方かける。留保は落とさず運ぶ
- 結果がおかしいときは、まず指示を疑う

セッションを束ねる道具立て自体は今後も変わっていくだろうが、この辺の型は道具が変わっても残りそうに思う。
