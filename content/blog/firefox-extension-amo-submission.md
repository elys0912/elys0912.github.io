# はじめに

Claude Code から普段使いの Firefox を読んだり操作したりする拡張を、自分用に作って使っている。ログイン済みの本物のプロファイルで、ページを読む、要素を探す、スクリーンショットを撮る、クリックする、入力する、といったことを AI にやらせる。

作ったきっかけは、Chrome を使ってる友人ともくもく会をやっていて、うらやましくなったから。

自分用なら署名だけして配る（unlisted）で済む。今回は、Firefox の公式アドオンストア（AMO）に載せる（listed）ことにした。載せるとなると審査がある。自分用で緩くしてたところが、そのままでは通らない。

作業は AI（Claude Code）と壁打ちしながら進めた。何を外し、何を残すかは自分で決めている。

# 規約を一次資料から写す

最初にやったのは、AMO の規約を読むこと。Add-on Policies、ソースコードの提出、データ収集の申告、提出の手順、安全な拡張の作り方、MV2 の方針、の 6 本を要点にして、レビューの基準として 1 つの文書に写した。

AI に「AMO の規約に合うか見て」と頼むだけだと、記憶の中の古い規約で判断されるかもしれない。基準を先に文書にしておけば、指摘ごとに「規約のどこか」を示させられる。

# 2 つのモデルで洗い出す

観点を 3 つに分けた。

| 観点 | 中身 |
|---|---|
| 規約適合 | 規約の条文に合っているか |
| 審査・配布の実務 | 審査者が確かめられるか、ソースの提出とビルド |
| 安全性・利用者保護 | 利用者が知らないうちに何かが起きないか |

観点ごとに、Sonnet と Opus に互いの結果を見せずに独立で洗い出させた。1 周目は 73 件。2 周目は Opus に、1 周目の全件をコードと規約で反証させて、同じ原因のものを束ねる形にしてある。

| 観点 | 1 周目 | 確認／修正／棄却 | 束ねた後 | 両方が出した |
|---|---|---|---|---|
| 規約適合 | 24 | 15／8／1 | 14 | 9 |
| 審査・配布 | 22 | 12／10／0 | 10 | 8 |
| 安全性 | 27 | 14／11／2 | 17 | 6 |
| 計 | 73 | 41／29／3 | 41 | 23 |

両方のモデルが出したのは 41 件中 23 件。残りは片方しか見つけていない。1 つのモデルだけに見せていたら、半分近くを落としていたことになる。

観点をまたいで束ねると、必須の指摘は 4 つの原因に集約した。

1. 外から来たコード文字列の実行
2. データ収集の申告の誤り
3. プライバシーポリシーが無い
4. ソースの提出と、再現できるビルドが無い

# 直したこと

## コード文字列の実行を経路ごと消す

自分用では、手元のプログラムから届いた文字列を、ページの中でスクリプトとして実行できた。規約では、拡張は自分の中で完結していなければならず、外から来たコードを実行してはいけない。設定で無効にしておく案も考えたけど、配る拡張の中に経路が残る。経路ごと消して、ビルドした成果物にその呼び出しが無いことをテストで確かめるようにしてある。

ページの記録（logging）も外した。1 回始めるとサイトをまたいで本文を記録し続け、記録中の表示も無かった。

## データの申告とマスク

最初は「データを集めない」と申告してた。拡張から手元のプログラムに送るだけで、開発者のサーバーには何も送らないからだ。ただ、規約では手元のプログラム（native messaging）への送信もデータの送信に入る。そこから先は MCP クライアントを経由して AI の提供元に届く。

ページの内容、閲覧の履歴、サイトでの操作の 3 つを申告した上で、送らない値のマスクを広げた。パスワード欄だけだったのを、hidden、ワンタイムコード、クレジットカードの欄にも広げている。

## 利用者が止められるようにする

自分用は、起動したら無条件に手元のプログラムにつながっていた。公開用では次のようにした。

- 初回に許可の画面を出し、許可するまでつながない
- ツールバーから一時停止できる
- 操作中はバッジを出す
- クリック・入力・ナビゲーションは、どのサイトでも毎回人の承認を待つ
- private browsing では動かさない

自分用は「サイトの一覧に載っているところだけ確認する」形だった。一覧はアメリカのサイトが中心の 16 件で、配る前提だと地域で偏る。全部のサイトで操作は確認する形にした。

## 再現できるビルド

AMO はビルドしたコードを提出するとき、ソースも一緒に出させる。審査者がソースから同じ成果物を作れなければならない。

調べると、作業ツリーの改行が CRLF の混在になっていて、成果物に入るファイルが Linux でビルドしたものと一致しなかった。.gitattributes で改行を LF に固定し、OS と Node・npm の版、ビルドのコマンドを手順書に書いた。

## 審査者が試せるようにする

この拡張は、手元のプログラムと MCP クライアントが無いと何もしない。審査者が Claude Code を入れずに試せるよう、ローカルのテストページで基本の動きを試すスクリプトと、審査者向けのメモを付けた。

# 自分用と公開用を分ける

最初は、1 つのリポジトリからビルドの切り替えで自分用と公開用を作り分ける案だった。ただ、AMO 上では同じ ID の listed と unlisted は 1 つのアドオンとして扱われるので、ID を分ける必要があった。インストーラーも診断のコマンドも 1 つの ID しか扱わないので、作り分けるとそこも全部直すことになる。

結局、公開用は別のリポジトリにして、名前も ID も変えた。作り分けの仕組みは要らなくなった。

切り替えの仕組みを作って守り続けるより、2 つに分けて片方は緩いままにしておく方が、自分用の方を触るときに気を使わなくて済む。

自分用の KitsuneMCP は緩いまま残し、公開用は Inari MCP for Firefox にした。「Kitsune」は Mozilla のサポートサイトの基盤と同じ名前なので、公開用では避けた。名前は、お狐さんに奉納するといえば稲荷、というだけ。

# 審査の結果

通った。2026-10-14 に提出して、当日のうちに承認（AMO の掲載も 2026-10-14 付）。差し戻しは無し。[AMO のページ](https://addons.mozilla.org/ja/firefox/addon/inari-mcp-for-firefox/)に 0.1.0 が載ってる。

提出の前に 2 つのモデルで 73 件を洗って 4 つの原因に束ねた分が、そのまま効いた形になる。審査者向けのメモとローカルのテストページも付けてあるので、向こうで試して詰まるところが無かったのかもしれない。

公開した後にやったのは、次の版を出すときの手順を手順書に足したくらい。2 回目からは「Upload New Version」で、変更履歴のその版の節を Version Notes に貼り、プライバシーポリシーの URL を新しいタグに合わせる。利用者に見える変更が貯まるまで、版は上げない。次を出すのは、そのときか。

# まとめ

- 規約は一次資料から写して、レビューの基準にする
- 2 つのモデルに独立で見せると、片方だけが見つけるものが半分近くある
- 「設定で無効」ではなく、配る成果物から経路ごと消す
- 自分用と公開用は、無理に 1 つにまとめない

自分用で便利だった機能のいくつかは、公開用では外すか、確認を挟む形になった。人に配るなら、それくらいでちょうどいいのかもしれない。
