# はじめに

フクダ電子アリーナの非公式の座席表を作った（概要は作品ページにある）。席は生成した数で 18,990。スマホで全体から 1 席まで寄れて、タップした席を引けることを要件にしている。

席の数がこれだけあると、描き方で使い心地が決まる。結論はフレームワークを使わず TypeScript と Canvas 2D だけで描くこと。設計は AI（Claude Code）と壁打ちしながら詰め、案の取捨はこっちで決めた。この記事はその描画と逆引きの中身を書く。

# 席ごとに要素を持たない

最初に外したのは「席 1 つにつき DOM か SVG の要素を 1 つ」という作り。約 1.9 万の要素を作り、ピンチのたびに位置を更新するのは、スマホでは重いと見た。正直に書くと、SVG で全席を描く案は測って捨てたわけではない。設計の早い段階のメモで「モバイルで重い」と見積もり、LOD か Canvas を検討する方向に進んだ。

Canvas なら 1 枚の絵なので、倍率に応じて描く量を絞れる。状態も「視点（倍率と平行移動）・選択した席・席種の設定」の 3 つしかない。

フレームワークは Svelte 5 と SolidJS も候補に挙がった。とはいえ中身は Canvas と小さな検索フォームだけで、仮想 DOM の再描画の単位と Canvas の描画の単位がそもそも合わない。ブログを素の TypeScript で作り直した流れもあって、フレームワーク無しに決めた。実行時の依存は 0 で、ビルドは esbuild 1 本で済んでいる。

# LOD を 4 段で切り替える

描くものは「画面上の席の間隔 d」で決める。d は区画ごとの席の間隔（メートル）に倍率を掛けた値で、段は区画ごとに持つ。

| 段 | 描くもの | 拡大で入る | 縮小で戻る |
|---|---|---|---|
| 0 | 区画の塗りと外形、席種の略称 | — | d < 2 px |
| 1 | ＋列ごとの線 | d ≧ 3 px | d < 6 px |
| 2 | ＋席を正方形で | d ≧ 7 px | d < 11 px |
| 3 | 席を円で | d ≧ 12 px | — |

入る値と戻る値をずらしてあるのがヒステリシス。段 2 に入るのは 7 px からだが、段 1 に戻るのは 6 px を割ってからになる。閾値が 1 つだと、ちょうどその倍率でピンチを止めたとき、指のわずかな揺れで段が行き来して画面がちらつく。境目に幅を持たせておけば、それが起きない。

段を区画ごとに持たせたのは、席の間隔が区画で違ったため。初期のパラメータではメイン・バックの間隔が北・南の約 2 倍あり、同じ倍率でもメイン・バックが先に席を描く段に入った。後でデータを差し替えてからは、どのスタンドも 0.43〜0.45 m でほぼ揃っている。

ほかにも描く量を絞る所がいくつかある。

- 画面の外の区画と席は描かない。区画の外接矩形で粗く絞ってから、席の座標で絞る
- 段 2 は席種の色ごとに `fillStyle` を 1 回だけ設定して、`fillRect` を続けて呼ぶ。`fillRect` はパスに入らず、その場で描かれる。段 3 は色ごとに `arc` をパスに積んで `fill` を 1 回
- ピンチやドラッグの最中は段を 1 つ下げて描き、指が止まったら本来の段で描き直す
- 席のループの中では座標変換の関数を呼ばず、式を展開して書く。1 フレームに数千回呼ぶので、そのたびにオブジェクトを作るのを避けた

一番重いのは PC の画面で全体に近い倍率のときと見積もっている。メイン・バックだけが段 2 に入って、約 9,300 席を描く。1 万回の `fillRect` なら 1 フレームの内に収まる見込み。

初期描画の時間と操作中の fps は、`?debug` を付けると測れるようにしてある。実測はまだしていない。

式を展開した件には代償もあった。後で画面の向きを公式の座席図に合わせて 180° 回したとき、座標変換の関数を直すだけでは済まず、展開した式も一緒に直している。速さと引き換えに、同じ式を 2 か所で持つ形になっている。

# タップした席を逆算する

席ごとの要素が無いので、ブラウザの当たり判定は使えない。タップした点から、席を計算で求める。

座席は最前列の曲線（直線 4 本と角の円弧 4 本の閉曲線）を外側へずらして列を作っている。逆引きはこれを逆にたどる。

1. タップした画面の座標を、ピッチの中央を原点にした論理座標（メートル）に戻す
2. 最前列の曲線の各片（直線か円弧）に点を射影し、曲線に沿った位置（弧長）と外向きの距離（奥行き）を出す。片の帯に入るものの中で、奥行きの絶対値が一番小さいものを採る
3. 弧長からスタンドと区画を決める。通路の上なら席なし
4. その区画の 2 階の開始列を使い、奥行きから列を決める。2 階との段差の中や最後列の外なら席なし
5. その列の先頭の位置と席の間隔から何番目かを出し、「その列の先頭の番号 + 何番目か」を番号にする

この順序には意味がある。2 階が何列目から始まるかは区画ごとに違うので、奥行きを列に直すには先に区画が要る。

距離の閾値も置いていない。列は奥行きの帯、番号は何番目かで決まるので、「席の中心から何 px 以内」という判定が要らない。ピッチの上、通路、内側の列で席の無い両端は、それぞれの段で null になる。

角度を使う所は向きを間違えやすかった。論理座標は左手系なので、`atan2` が増える向きは番号が増える向きと逆になる。そもそも番号の向きも調べた結果を一度「時計回り」と書いて、後で反時計回りに直した経緯がある。今は各スタンドの 1 番がどの象限にあるかをテストで固定し、生成した全席の中心から逆引きして同じ席に戻ることも確かめている。

# 引き受けたこと

- 席ごとの要素が無いので、スクリーンリーダーで席をたどれない。代わりに、席種・列・番号の検索フォームと結果のポップアップを用意した
- 逆引き、LOD、ラベルの配置は全部自前で持つ。描画の崩れは自動テストでは見えないので、手で確かめる項目を README に並べてある
- 目標は初期描画 1 秒以内、操作中 30 fps 以上。割ったら、まず LOD の閾値と画面外の絞り込みを見直す。それでも足りないときだけ、描画ライブラリ（PixiJS など）を検討する

# まとめ

- 席ごとの要素は持たず、Canvas 1 枚に描く量を倍率で絞る
- LOD は区画ごとの席の間隔で決め、閾値に幅を持たせてちらつきを消す
- 逆引きは描いた計算を逆にたどる。区画 → 列 → 番号の順にしか決まらない

要素を持たない代わりに、当たり判定や読み上げのようにブラウザがただでやってくれていたことを、こっちで持つことになる。1.9 万という数なら、その交換は割に合ったと思う。
