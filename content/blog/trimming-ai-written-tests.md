# はじめに

ポートフォリオのサイトのテストは、ほぼ全部 Claude Code が書いている。テストのファイルに触ったコミットは 106 本あって、106 本とも Claude Code との共作になっている。

AI にテストを書かせると、頼んだ分よりだいぶ多く出てくる。境目の値、null、空文字、同時実行、と思いつく限り並べてくる。1 本ずつ見ると間違ってはいない。ただ、積もると直すたびに書き換えるテストが増えて、何を守っているのか分からないテストも混ざってきた。

そこで、既存のテストを見直して、消す基準に当たるものを消した。この記事はその基準と、消した例の話。

# なぜ増えたか

理由は単純で、AI は「念のため」を止めない。機能を 1 つ足すと、その機能の正常系、境目、異常系をそれぞれ書く。さらに、別の Spec で確かめていることも「この Spec の責務だから」ともう一度書く。

最初に気づいたのは別のリポジトリだった。Firefox 拡張を作っていたとき、1 つのファイルを書いた直後に 42 件のテストが出てきた。そこで「人が使う場面と、閾値（境目の値）だけでいい。件数を水増ししない」と Claude Code に伝えて、19 件に絞り直した。今は CLAUDE.md にも「テストは振る舞い（入出力・副作用）に書く。モックの戻り値を assert するだけのテスト、フレームワーク自体のテスト、実装手順の写経テストは書かない」と書いてある。

ただ、ルールを足しても、それより前に書いたテストはそのまま残る。ポートフォリオのテストは、ほとんどがルールより前のものだった。

# 消す基準を先に決めた

いきなり「要らないテストを消して」と頼むと、AI は消す理由を後から作る。なので、先に基準を決めて、どれかに当たるものだけを消すことにした。

1. ほかのテストや検査用データと、同じ入力・同じ経路を通る
2. 実装や定数を写している
3. フレームワークの動作を確かめている
4. 起こり得ない入力を確かめている
5. 書き方の規約を確かめている

範囲は backend の 2048 の Spec、frontend の 2048 と座席表、infra の CDK のテスト。ほかの作業と同時に直す予定のファイルは外した。

## 1. 同じ入力・同じ経路

2048 の再生は検査用データ（テストベクタ）を TypeScript と Java の両方に流している（[別の記事](/posts/test-vectors-across-three-languages/)に書いた）。このデータには「長すぎる」「不正な文字」「盤面が動かない手」の失敗のケースが入っている。

それとは別に、Java には長さの境目（50,000 手と 50,001 手）を確かめる Spec と、不正が重なったときの検査の順序を確かめる Spec があった。TypeScript にも同じ内容のテストがあった。検査用データで同じことを確かめているので、Spec 2 本と、TypeScript 側のテストを消した。

DB の一意制約も、テーブルの制約をまとめて確かめる Spec と、リポジトリの Spec の両方にあった。こっちもリポジトリの側を消した。

## 2. 実装や定数の写し

いちばん分かりやすいのがこれ。

```ts
test("既定の上限は 10 秒（仮）", () => {
  assert.equal(REQUEST_TIMEOUT_MS, 10_000);
});
```

定数を 10 秒と書いて、テストでも 10 秒と書いている。上限を変えたら、両方を直すだけで終わる。守っているものが無い。

ハッシュのテストも同じ形だった。実装と同じ手順で SHA-256 を計算して、結果が一致するかを見ている。実装を写しているだけなので、手順を間違えたら両方とも同じように間違える。

## 3. フレームワークの動作

ランキングを取るときの件数が 1 未満なら例外になる、という Spec があった。この例外を投げているのは Spring Data の `PageRequest` で、自分で書いたコードではない。件数の範囲は API の側で確かめて 400 を返す前提で、リポジトリに不正な値は来ない。Spec ごと消した。

## 4. 起こり得ない入力

名前の検査に `null` を渡すテストや、トークンの照合に `null` を渡すテストがあった。どちらも消した。

## 5. 書き方の規約

infra には「生成したコードが ES5 の書き方になっている」を確かめるテストがあった。ES5 にそろえているのは、CloudFront Functions の対応の範囲を調べずに済ませるためで、動作の要件ではない。テストは消して、そろえていることと、それを検査していないことをコメントに書いた。

# 消してよいかの確かめ方

消す作業も Claude Code に任せた。ただ、消すのは足すより怖い。消したテストが実は唯一の検査だった、が一番まずい。

なので、消す前に別のセッションの Claude Code にレビューさせた。承認したのはこっち。

消した後は、変えたファイルだけをテストした。frontend は 217 件、infra は 55 件が通った。backend は Docker が要らない 7 本が通り、DB を使う 4 本は手元に Docker が無いので CI で確かめた。

結果として、テストメソッドは差し引き 50 本減った。59 本を消し、そのうち 9 本は中身を絞って書き直している。行数は約 600 行減って、足したのは 23 行。

# おわりに

AI にテストを書かせると、量は勝手に出てくる。足りなくなるより、多すぎることのほうが多い。多すぎるテストは直すたびに一緒に書き換える手間になって、本当に守りたい境目が埋もれる。

足すときのルールは書いた。消すときの基準も書いた。
