# はじめに

Claude Code にはメモリがある。作業ディレクトリごとに `~/.claude/projects/<名前>/memory/` ができて、1 つの事実が 1 ファイル、索引が `MEMORY.md`。セッションをまたいで「この PC では AWS CLI が使えない」「このリポジトリの main には直接 push しない」といったことを覚えておいてくれる。

困るのは、これが PC ごとに溜まること。会社の PC と自宅の PC で同じリポジトリ群を触っているので、片方で覚えたことをもう片方でも使いたい。この記事はそれを git で同期するようにした話。仕組みは Claude Code と壁打ちしながら作り、どこまで自動にするか、何を同期しないかはこっちで決めた。

# 手で写していた頃

最初は手動だった。メモ用の private リポジトリに `tools/claude-share/` を作り、シェルスクリプトで `export`（手元 → repo）と `import`（repo → 手元）をする。更新した PC が export して push し、他の PC が pull して import する。

これが 2 週間半ほどで破綻しかけた。忘れると差分が溜まる。それだけならいいが、`export` は repo 側を手元の内容で丸ごと置き換える。他の PC の追加を import し忘れたまま export すると、その追加が消える。消えたことに気づくのは、消えた後。

# 自動化の形

セッションの開始と終了に Claude Code の hooks でスクリプトを呼ぶ形にした。`SessionStart`（`startup` と `resume`）と `SessionEnd` に `sync.sh sync` を登録する。1 回の動きは次のとおり。

1. 手元のメモリを repo の置き場へ反映する
2. その置き場だけを commit する
3. `git pull --rebase --autostash`
4. push
5. repo の内容を手元へ写す

1 回で数秒。stdout には何も出さず、ログファイルにだけ書く。セッションの開始に文字が流れるのは邪魔だから。

同期するのは個人開発のメモリだけにした。業務のメモリは原文に IP やドメインが入るので、伏字にした写しを手動で運ぶ従来の形のまま。自作の Skill も同じ。全部を自動にする案もあったが、伏字の仕組みが絡むところは手でやるほうが安心できる。

競合は自動で解かない。同じメモリが両方の PC で変わっていたら rebase を中止し、手元も repo も変えずにログへ `CONFLICT` と書く。次のセッションで `git status` を見て手で直す。索引の `MEMORY.md` だけは `.gitattributes` で `merge=union` にして、両方の行を残す。索引は 1 行 1 メモリの一覧なので、両方残せば正しい。

ほかに捨てた案は 2 つ。メモリのフォルダー自体を git リポジトリにする案は、repo が 1 本増えて伏字と Skill の配布が別の置き場に分かれる。OneDrive に置いてジャンクションを張る案は、両方で同時に書くと競合ファイルができるし履歴も残らない。

# 片方の PC でしか正しくないメモリ

同期を始めると、「この PC では」と書いたメモリが嘘になる。会社の PC では gh が無い、実機の確認ができない、といった事実は、自宅の PC では当てはまらない。

`.gitignore` で PC 固有のメモリを外す案は捨てた。索引に片方にしか無い行が残ってリンク切れになる。代わりに、本文に「会社 PC では」のように対象の PC を書くことにした。自宅の PC は複数あるので、会社とそれ以外が区別できれば足りる。既存のメモリの「この PC」は書き換えてある。

# 最初の版は巻き戻す作りだった

動かし始めた日に、別の PC で `git pull` を手で流した後の差分を見たら、手元の 15 ファイルが古く、repo にしか無いメモリが 1 件あった。hooks を入れる前に手で import していたので実害は出なかったが、入れていたら消えていたはず。

原因は手順 1。最初の版は手元のメモリを repo の置き場へ「丸ごと写す」だった。置き場を消して手元の内容で作り直し、commit する。手元が repo の作業ツリーより古いと、その内容がそのまま commit されて pull、push まで進む。困る場面は 3 つあった。

- 別の PC で hooks を入れた直後。手元の写しが古い
- notes を手で `git pull` した後。sync 以外の経路で作業ツリーだけ新しくなっている
- 手元に置き場が無いときは何もせずに終わる。手順書に書いた「最初の sync で repo のメモリが手元に入る」と逆の動き

直し方は最後に同期した commit を手元に記録しておくこと。手元 → repo の手順では、その版と比べて手元で変わった・消えたファイルだけを送る。記録が無い初回は手元 → repo を飛ばし、pull と repo → 手元の写しだけを行う。手元にしか無いファイルは消さない。repo → 手元の削除も同じ記録を基準にし、最後に同期した版から repo で消えたファイルを手元からも消す。

「初回だけ直す」という小さい案もあったが、手で pull した後の巻き戻りは防げない。「引き継ぎ書に注意書きを足す」案は、人の注意に頼ることになる。忘れたから自動化したのに、また忘れないことを前提にするのは筋が通らないだろ。

直すときは一時的な clone を 2 つ作り、PC a と PC b に見立てて 3 つの場面を再現するテストを 17 件書いた。テストが先に落ちて、もう 1 つ不具合が見つかった。削除の伝播で相対パスにするべき変数が絶対パスのままで、手順 5 の削除は一度も動いていなかったことになる。

# 残っている悪い面

- メモリの本文が private とはいえ GitHub に置かれる。個人情報や認証情報を書かない運用が前提
- notes の作業ツリーを他のセッションと共有するので、`--autostash` で退避した変更を戻すときに競合すると同期が止まる
- ネットワークが無いと pull と push が失敗する。ログに残るだけで、メモリは手元のまま
- 競合を放置すると両方の PC の差分が広がる

# AI との付き合い方

スクリプトも hooks の設定も、Claude Code が書いた。こっちがやったのは、同期の対象を個人開発のメモリに絞ること、競合を自動で解かないと決めること、巻き戻りの不具合をどう直すか 3 案から選ぶこと。

巻き戻りの不具合は、Claude Code の説明を読んだだけでは「初回だけ直す」で済む気がした。3 つの場面を並べてもらって、初めて「手で pull した後」が残ると分かった。場面を列挙させてから選ぶやり方は、今後も続けたい。
