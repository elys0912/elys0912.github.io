# はじめに

このサイトには 2048 が置いてあり、スコアのランキングが付いている。ランキングを作るとき最初に決めたのは「コンソールからの操作や API の直叩きによる不正なスコアは、確実に弾く」こと。ゲームはおまけでも、嘘のスコアが並ぶランキングは置く意味がない。

設計は AI（Claude Code）と壁打ちしながら進め、どの案を採るかは自分で決めた。この記事は、その不正対策の作りを書く。

# スコアは受け取らない。手の列を受け取る

一番の肝はここ。クライアントが「スコア 50000 でした」と送ってくる値は、何を検査しても信用できない。なので API はスコアの項目を受け付けない。

流れはこうなっている。

1. ゲーム開始時に、サーバーが乱数の種（seed）を渡す
2. ブラウザはその種でタイルを出しながらゲームを進める
3. 登録時に送るのは、押した方向の並び（手の列）だけ
4. サーバーが同じ種と手の列からゲームを再生し、スコアを自分で計算する

盤面やスコアをコンソールで書き換えても、サーバーの再生には反映されない。動かない手や終局の後の手が混ざっていれば、再生の途中で見つかって 400 で弾かれる。乱数生成器（mulberry32）は TypeScript と Java で同じ実装を自前で書き、検査用のデータをリポジトリに置いて両方のテストで突き合わせている。

# 再生だけでは防げないもの

| 不正 | 止め方 |
|---|---|
| 同じセッションで 2 回登録 | used_at を条件にした 1 回の UPDATE で使用済みに。2 回目は 409 |
| 古いセッションの使い回し | 有効期限 24 時間。過ぎたら 410 |
| 人間には無理な速さ | サーバーの時刻で「経過時間 ≧ 手数 × 1 手の下限」を検査 |
| セッションの大量生成・連打 | 接続元ごとの回数の上限と、ゲーム用ルートだけの throttle |
| 巨大なリクエスト | 手の列は 50,000 手まで、本文は 64KB まで |

一方で、防げないと割り切ったものもある。種はブラウザに渡すので、この先に出るタイルは読める。つまり、自動で解くプログラムが正しい手を打ってくる不正は、再生しても見分けられない。1 手ごとにサーバーがタイルを出す方式なら先読みは防げるが、1 ゲームで数千回 API を呼ぶことになって遅さと費用が見合わないので、却下した。

ここは「時間の下限と回数の上限で抑え、残りは管理用の削除で拾う」という二段構えにしてある。完璧を目指すと費用が跳ねる。個人サイトのおまけのゲームに守らせる水準としては、これで十分とされる。

# 細かい決めごと

- **同点は登録が早いほうが上**。DB からは上位 N 件に同点の分を足して取り、アプリ側でスコアの降順・登録の昇順に並べ直す
- **名前の変更は登録直後だけ**。編集用のトークンは 256 bit の乱数で、DB にはハッシュだけ置き、返すのは登録の応答の 1 回だけ。ブラウザには保存しない
- **接続元の判定に X-Forwarded-For は使わない**。先頭は利用者が偽れるので、CDN が付け直すヘッダーを使う。生の IP は保存せず、ソルト付きのハッシュにする
- **保持期間はセッション 7 日・スコア 14 日・上位 20 件まで**。消すのは毎日のスケジュール実行。個人サイトのランキングに永続の個人データを置かない
- **管理用の削除は HTTP の入口を作らない**。管理 API をルートに生やすと、認可の判定を誤ったときに穴になる。Lambda を IAM で直接呼ぶ形にして、外から呼べる経路をそもそも無くした

# まとめ

- スコアは受け取らない。種と手の列から、サーバーが再生して計算する
- 防げない不正（自動で解く系）は線を引いて受け入れ、時間・回数・削除で抑える
- 管理の入口は作らないのが一番安全

「クライアントを信用しない」は言い古された原則だが、ゲームだと「スコアを検査する」ではなく「スコアを受け取らない」まで振り切れるのがおもろいところ。再生という答え合わせの手段がある題材なら、同じ形が使える。
