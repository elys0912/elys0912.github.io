# はじめに

このサイトの AWS の請求は、10 月のここまでで $0.024。8 割が S3 の PUT で、残りはほぼ 0。月 3 円ちょっと。削ってもお金は増えない。

それでも掃除をしたのは、放っておくと増え続けるものが 3 つ見つかったから。期限なしのロググループ、失敗したデプロイが残したロググループ、デプロイのたびに溜まる CDK のアセット。どれも今は小さいが、止める仕組みが無い。

作業は AI（Claude Code）と壁打ちしながら進めた。何を消すか、どこまで AI に任せるかはこっちで決めている。

# ロググループ

## 期限なしが 7 個

公開前のチェックで、ロググループの保持期間を実物で確かめた。`describe-log-groups` で東京リージョンに 14 個。このサイト用に書いた Lambda（API、マイグレーション、ゲームの管理）は 30 日で、プライバシーポリシーの「1 か月で消える」と合っている。

合っていなかったのは、CDK が勝手に作る Lambda のほう。Trigger や S3 の autoDeleteObjects のようなカスタムリソースの Lambda が 7 個あって、ロググループは全部「期限なし」だった。中身は CloudFormation のイベントだけで、量としては知れている。とはいえ、期限なしは期限なしなので、Aspect で 30 日のロググループを付けて回るようにした。CDK のコンストラクトを全部たどって、該当する Lambda にロググループを足す形になっている。

## 失敗したデプロイの孤児が 9 個

もう 1 つは、9 月に失敗したデプロイの残骸。スタックがロールバックしたときに、ロググループだけが取り残されたようだ。API が 1 個、マイグレーションが 3 個、Trigger が 5 個。

[CloudFront の記事](/posts/cloudfront-static-and-api-pitfalls/)に「ロググループがロールバックで消える」と書いたが、こちらはロールバックで消えずに残ったもの。残す設定は正しい。原因を追うためのログが、原因が起きたときに消えるのは困る。ただ、残したものを消す手順が無かった。使用中かどうかは `aws lambda list-functions` の `LoggingConfig.LogGroup` で見分けられる。

# CDK のアセット

## 1.7GB 溜まっていた

アセット用のバケットを見ると 1.7GB あった。原因は backend の zip。`cdk deploy` はデプロイのたびに約 60MB の zip をアセット用のバケットに上げる。10 月は main に push するたびにデプロイしていたので、月に 60 回以上。

CDK のブートストラップが作るバケットには、もともと「古いバージョンを消す」ライフサイクルが付いている。効いていない理由は、キーが中身のハッシュだから。中身が違えば別のキーになり、上書きが起きない。「古いバージョン」が一度も生まれないので、このルールは一度も効かないんだよな。

## ライフサイクルで消してはいけない

最初に思いつくのは「作成から N 日で消す」ライフサイクルを足すこと。これはやってはいけない。

デプロイ済みのスタックは、今の zip を参照している。それが消えた状態で次のデプロイが失敗すると、CloudFormation は前の版に戻そうとして、戻す先の zip が無い。スタックは `UPDATE_ROLLBACK_FAILED` で止まるはずだ。したがって、消したい「古い zip」と、消してはいけない「今使っている zip」は、作成日では区別できない。

## cdk gc で 2 段の退路

そこで使うのが `cdk gc`。デプロイ済みのスタックのテンプレートを読んで、どのスタックからも参照されていないアセットを探す。参照の有無で判定するので、作成日の問題が無い。

月 1 回、GitHub Actions から回すようにした。退路は 2 段にしてある。

1. 1 回目の実行では「孤立」のタグを付けるだけ。猶予日数（7 日）を過ぎたものを、次の実行で消す。デプロイの途中で上がったアセットにタグが付いても、次の実行までに参照されればタグが外れる
2. バケットはバージョニングが有効なので、消したアセットも古いバージョンとして 30 日は戻せる

Actions のロールに付く権限は、CloudFormation の読み取りと、アセット用のバケットのタグ付け・削除マーカーの追加だけ。バージョンそのものは消せないので、ロールが乗っ取られても 30 日は取り返せる。

手元で試しに回すと、73 個（1.43GiB）が参照なしの判定になった。削除は 0 個。タグを付けただけで、消えるのは猶予が過ぎた後の実行になる。

# AI に任せたら 3 回止められた

この作業の途中で、Claude Code の自動モードの安全判定に 3 回止められた。

1. ロググループの削除
2. 確認を飛ばしてコマンドを通す操作
3. 自分の権限のルールの書き換え

どれも「人間が決めるべきこと」として止まった形で、判定としては正しい。削除は取り返しがつかないし、確認を飛ばすのは自動モードの前提を崩すし、自分の権限を自分で広げるのは論外だ。

ここで決めたのは、権限の線引きは人間が決め、AI は決めた範囲の中で動く、ということ。練習を兼ねて、許可するコマンドのルールを書いた。読み取りの `describe-*` や `list-*` は通す、削除は通さない。ロググループの削除は、使用中かどうかを見分けてから、手で実行する。

# まとめ

- 「期限なし」は、量が小さくても期限なし。CDK が勝手に作るものにも保持期間を付ける
- 残す設定にしたログは、消す手順もセットで用意する
- キーがハッシュのバケットでは「古いバージョンを消す」ルールは効かない
- 作成日で消すと、ロールバックの戻り先まで消える。参照の有無で消す
- 消す前にタグ、消した後にバージョニング。退路は 2 段
- 削除は AI に任せず、権限の線引きは人間が書く

削減額は月数セントにもならない。それでも、増え続けるものを仕組みで止めておけば、後で見に来る必要がなくなる。見に来る時間のほうが、よほど高くつく。
